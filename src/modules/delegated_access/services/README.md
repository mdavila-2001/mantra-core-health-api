# Servicios — delegated_access

Poseen la unidad de trabajo (`em.transactional`), validan precondiciones y lanzan
excepciones de dominio (`ResourceNotFoundException` → 404, `ConflictException` →
409, `PreconditionFailedException` → 422, `ConcurrencyConflictException` → 409).
Cada escritura relevante deja un asiento en `delegation_events`.

| Servicio                           | UCs                                                    |
| ---------------------------------- | ------------------------------------------------------ |
| `OrgUserAssignmentsService`        | UC-29-01 (crear), UC-29-10 (patch/suspender)           |
| `PermissionSetsService`            | UC-29-02 (crear set + versionar)                       |
| `PractitionerDelegatesService`     | UC-29-03 (crear), UC-29-06 (grant), UC-29-07 (revocar) |
| `AccessRequestsService`            | UC-29-04 (solicitar), UC-29-05 (decidir)               |
| `DelegatedAccessEvaluationService` | UC-29-08 (barrido), UC-29-09 (evaluar)                 |

`concept-maps.ts` traduce los enums de los DTO a `*_concept_id`. Specs unitarios
(`*.service.spec.ts`) mockean repositorios y `EntityManager`.

## Política con gobierno de accesos (v4.2.72)

`SupportAccessPolicy` sigue siendo la puerta (`can`, `canReplyOnBehalf`,
`canReplyOnBehalfActing`, `canSearchPatients`, `filterSearchResults`,
`evaluatorFor`); la decisión completa la orquesta `SupportDecisionPipeline`. Sin
el pipeline (las pruebas antiguas construyen la política con tres argumentos) la
política decide como antes del gobierno: sin reglas, condiciones ni registro.

| Pieza                                                                                                                                                     | Responsabilidad                                                                                                                                                                                                                                                                |
| --------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `support-decision-pipeline.ts`                                                                                                                            | Una decisión: reglas L1, contexto del servidor (IP, sesión, `X-Approval-Id`), aprobación, motor puro, consumo (aprobación y contadores, todo o nada), registro y estadística. También `prepareListing` (agenda), `filterPatients` (búsqueda) y `evaluateStructure` (listados). |
| `support-access-context.loader.ts`                                                                                                                        | PIP perezoso: carga solo los hechos que el motor toca (`requiredFacets` acota la cota superior). Sin condiciones no consulta nada.                                                                                                                                             |
| `support-access-context.ports.ts`                                                                                                                         | Puertos del PIP (paciente, sesión, red, dispositivo, presencia, paso extra, zona). Los adaptadores viven en `../infrastructure/adapters/`.                                                                                                                                     |
| `support-usage-counter.ts`                                                                                                                                | Contadores de `limits` y `amount` en Redis (Lua atómico, todo o nada); degrada a memoria por réplica sin abrir el tope.                                                                                                                                                        |
| `support-governance-rules.reader.ts`                                                                                                                      | Reglas L1 por organización con caché de 30 s; quien escribe una regla llama a `invalidate`.                                                                                                                                                                                    |
| `support-approval-gate.ts`                                                                                                                                | Comprueba y consume la aprobación de una acción (`X-Approval-Id`): misma persona, mismo átomo, mismo cuerpo, vigente, una sola vez.                                                                                                                                            |
| `access-decision-recorder.service.ts`                                                                                                                     | Bitácora WORM `access_decision_log`: todo `DENY`/`CHALLENGE` (deduplicado en proceso, sin `UPDATE`) y todo `PERMIT` de sensibilidad ≥ ALTA (obligatorio: si falla, `DENY DECISION_LOG_UNAVAILABLE`). Sin PHI.                                                                  |
| `access-usage-recorder.ts`                                                                                                                                | Estadística por hora (`grant_usage_stats`), buffer en proceso, vuelca cada 30 s o 200 eventos.                                                                                                                                                                                 |

| `governance-world.loader.ts`                                                                                                                              | Hechos de gobierno de una organización (vínculos, concesiones con átomos y condiciones, uso, otorgante, techo, SoD, aceptación del doctor); solo lee.                                                                                                                          |

| `access-review-automation.service.ts`                                                                                                                     | Recordatorios, escalamiento, ítems de recertificación a 30 días, campañas periódicas y de remediación, vencimiento de excepciones SoD.                                                                                                                                         |

| `access-review-concepts.ts`, `access-review-evidence.ts`, `access-review-input.ts`, `access-review-views.ts`                                              | Conceptos ↔ códigos, evidencia y su hash, validación del alcance y filtros, vistas de campañas e ítems.                                                                                                                                                                        |

La evidencia de cada decisión no lleva texto libre ni datos del paciente: solo
identificadores, códigos y números.

### Ciclo de vida, traspaso y administración delegada

| Archivo | Qué hace |
| --- | --- |
| `lifecycle.service.ts` | Ingreso (lista de 7 ítems, plazo de 7 días, `onboarding_completed_at`), dueño de la cuenta (D-07, GP-8), identidad registrada por un administrador, compromiso de confidencialidad de la persona, casos, registro de transferencia exportable y cuentas sin dueño. |
| `lifecycle-joiner-facts.ts` | Hechos que la lista de ingreso deduce sola: identidad de plataforma (criterio de `VerifiedIdentityGuard`), dos pasos y doctores que aceptaron. |
| `support-onboarding-gate.ts` | Compuerta de ingreso (D-03): alimenta `EngagementFacts.onboardingIncomplete`. Solo vínculos creados desde `onboardingRequiredSince`; sin consultas para el vínculo ya completo. |
| `support-lifecycle-settings.ts` | Ajustes `support.governance` que mandan en el ciclo de vida (inactividad, suspensión automática, revisión tras reactivar) y la exigencia de dos pasos de la política de sesión. |
| `engagement-move.service.ts` | Cambio de rol: lo anterior vence en `effectiveAt`, campaña `MOVER`, cuatro ojos si el puntaje sube más de 10 o aparece un átomo ALTA nuevo; ejecuta lo aprobado re-validando. |
| `engagement-suspension.service.ts` | Suspensión inmediata sin aprobación, suspensión del sistema por inactividad y reactivación siempre con cuatro ojos (D-19). |
| `engagement-handover.service.ts` | Baja con traspaso: valida, REVOCA y confirma, y solo después reasigna; un fallo del traspaso no deshace la baja; la cita pendiente no cambia de dueño (D-21). |
| `lifecycle-four-eyes.ts`, `lifecycle-approval-executors.ts` | Costura con `FourEyesService`: pide la solicitud y registra los ejecutores del cambio de rol y de la reactivación. |
| `lifecycle-review-opener.ts` | Abre las campañas `MOVER` y `TARGETED` (acción al vencer: solo escalar). |
| `grant-proposal.validator.ts` | Condiciones, barandillas (GP-1, GP-2, GP-5, GP-7, reglas `CEILING`) y segregación de funciones de lo que se propone otorgar. |
| `support-admin-directory.ts` | Administradores de seguridad, doctores, administradores delegados con su alcance y techo, y candidatos a dueño. |
| `team-admin.policy.ts` | Quién puede qué sobre quién (§6.4): alcance, techo efectivo, población administrable, GP-6 (nadie administra lo propio ni a otro administrador). |
| `team-admin.service.ts`, `team-admin-requests.service.ts`, `team-admin-cases.service.ts` | Rutas `/org/team/*`: personas, permisos, ciclo de vida, invitaciones, solicitudes por ítem y casos, siempre dentro del alcance. |
| `lifecycle-guard.ts`, `lifecycle.testing.ts` | Guarda de autorización que corre antes de escribir y doble en memoria para las pruebas. |
