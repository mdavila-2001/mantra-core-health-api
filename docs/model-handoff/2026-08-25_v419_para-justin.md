## 3 · Lo que te toca

### 3.1 · `ESTADO_DEL_VINCULO` — `src/modules/profiles/services/profiles-affiliations.service.ts:49-56`

Tu propio comentario decía *«cuando el value set exista, cambia este objeto y nada más»*. Existe:

```ts
export const ESTADO_DEL_VINCULO = {
  PENDIENTE: PROF.AFFILIATION_PENDING,
  DECLARADO: PROF.AFFILIATION_DECLARED,
  APROBADO: PROF.AFFILIATION_APPROVED,
  RECHAZADO: PROF.AFFILIATION_REJECTED,
  REVOCADO: PROF.AFFILIATION_REVOKED,
} as const;
```

Y borrá el bloque de comentario que explica el préstamo: ya no aplica.

### 3.2 · `estadoInicial()` — mismo archivo, líneas 146-166

Hoy devuelve **aprobado** en dos ramas donde nadie aprobó. La tabla nueva:

| Caso | Hoy | Debería |
|---|---|---|
| Sin sede (currículum) | `APROBADO` (L151) | **`DECLARADO`** |
| Sede sin organización a cargo | `APROBADO` (L162) | **`DECLARADO`** |
| Sede ajena **con** OWNER/ADMIN | `PENDIENTE` | `PENDIENTE` ✓ |
| Sede ajena **sin** nadie | `PENDIENTE` | **`DECLARADO`** |
| Sede propia | `APROBADO` | `APROBADO` ✓ |

El caso nuevo —«sede ajena sin nadie»— necesita preguntar si el tenant tiene alguna membresía
activa con `DIR.ROLE_OWNER` o `DIR.ROLE_ADMIN`. Es la consulta que convierte «declarado» en algo
distinto de «pendiente disfrazado»: si hay a quién pedirle permiso, se le pide.

### 3.3 · `visiblesDeTerceros()` — línea 129

`[ESTADO_DEL_VINCULO.APROBADO]` → `[APROBADO, DECLARADO]`. Si no, el currículum histórico (que
antes compartía concepto con «aprobado») desaparece del perfil público. Y el rótulo: donde el
vínculo esté **declarado**, la pantalla dice «declarado por el profesional, no confirmado por la
institución». Esa frase es parte del contrato, no una sugerencia de copy: es lo que compra el
derecho a publicar sin aprobación.

### 3.4 · El motivo, que ahora se guarda

- `rechazar()` / `decidir()` (líneas 238-320): escribir `solicitud.decisionReasonText = dto.reason`
  junto al cambio de estado.
- `RejectAffiliationDto` — `src/modules/profiles/dto/affiliation-request.dto.ts:55-75`: sacá el
  párrafo que dice «hoy el motivo **no se persiste**» y poné lo contrario, **incluido que lo lee el
  profesional**. Importa: quien escribe pensando que es una nota interna escribe otra cosa.
- La lectura del profesional tiene que devolverlo, o el rechazo sigue siendo mudo aunque el dato
  exista.

### 3.5 · El establecimiento en el alta

El DTO de alta acepta `healthFacilityConceptId`, validado contra `VS_BO_HEALTH_FACILITY` (patrón de
`vs_medical_specialty`: **422** si el uuid no es del conjunto). Es lo que alimenta el selector de
tu PR #223.

⚠️ **`findSame` en `practitioner-affiliations.repository.ts`** compara por `organization_name`. Con
la columna nueva tiene que comparar **por concepto cuando viene** y por nombre cuando no —igual que
los dos índices—. Si no, el alta duplicada con establecimiento pasa la comprobación previa, choca
contra `ux_practitioner_affiliations_same_health_facility` y el usuario ve un **500** en vez del
409. La constraint protege igual; lo que se pierde es el mensaje.

### 3.6 · Revocado

`AFFILIATION_REVOKED` existe en el conjunto pero **no hay endpoint que lo escriba**. Es el estado
que necesita el gating al aceptar del enunciado de MAC-VÍNCULO (revocado ≠ rechazado: uno estuvo
aprobado antes). Cuando lo agregues, el motivo va a la misma columna — por eso se llama
`decision_reason_text` y no `rejection_reason_text`.

### 3.7 · La escalera, del lado de la lectura

- `directory-read.service.ts:261-262` calcula `isVerified` como `=== TENANT_VERIFIED`. Con cuatro
  peldaños eso aplana ② y ③ a «sin verificar», que es exactamente lo que la escalera viene a
  evitar. Hay que exponer el peldaño, no un booleano.
- `directory-tenants.service.ts:191-201`: `verify()` exige `status === TENANT_PENDING`. Un tenant
  materializado desde el padrón o reclamado no pasa esa precondición.
- Front: `organization-panel.html:40-44` pinta un sello binario (Aprobada / Pendiente), y el estado
  del vínculo **hoy no se pinta en ningún lado** —`status` llega en el contrato y los dos mapeos lo
  descartan—. Con «declarado» eso deja de ser aceptable: es el estado que hay que mostrar con
  palabras.

### 3.8 · Las pruebas que se van a poner rojas

`profiles-affiliations.service.spec.ts` (12 referencias) y `profiles-practitioners.service.spec.ts`
(5). Las de `organization_extensions` usan `ORGEXT.AFFILIATION_ACTIVE`, que es otro concepto de
otra tabla: **no las toques**.

## 4 · Orden de despliegue (importa)

1. Tu PR con lo de §3.
2. Arrancar la API una vez: siembra los 7 conceptos y los 2 conjuntos.
3. **Recién ahí**, la segunda pasada del patch, que migra las filas existentes.

Si la 2.ª pasada corre antes que tu PR, las filas migran a `DECLARADO` y desaparecen del perfil
público (hoy `visiblesDeTerceros` sólo muestra `AFFILIATION_ACTIVE`), y cada alta nueva vuelve a
nacer en el concepto viejo. El patch está escrito para que eso no pase por accidente: si faltan los
conceptos, aborta con un mensaje que dice qué hacer.

El backfill mapea `AFFILIATION_ACTIVE → DECLARADO`, no a aprobado. Esas filas las «aprobó»
`estadoInicial()` sin que nadie las mirara: escribir aprobado sería fabricar un hecho.

`AFFILIATION_ACTIVE` y `_RETRACTED` siguen en el catálogo, deprecados, hasta que tu PR esté
desplegado y el backfill haya corrido en todas las bases. Después los borro yo, en un PR aparte.

## 5 · Cómo verificar de tu lado

```bash
# los siete conceptos existen tras arrancar la API
psql ... -c "SELECT code FROM terminology.catalog_concepts
             WHERE code LIKE 'profiles:AFFILIATION_%' OR code LIKE 'directory:TENANT_%';"

# el conjunto nuevo gobierna la columna
psql ... -c "SELECT target_table, target_column FROM system_context.dynamic_enum_bindings b
             JOIN system_context.dynamic_enum_definitions d ON d.id = b.dynamic_enum_definition_id
             WHERE d.code = 'practitioner-affiliation-status';"
```

Los dos índices parciales ya se ejercitaron con `INSERT` reales (transacción revertida): el
duplicado con establecimiento y el duplicado por nombre se rechazan cada uno por su índice, y dos
establecimientos distintos conviven.
